# 第一关 · 环境熟悉与基础 ROS 通信

环境说明：

- 系统：Ubuntu 20.04 LTS + ROS Noetic（官方培训镜像）
- 工作空间：`~/airhust_tutorial2026_ws/1关/airhust_tutorial26_ros_basics`
- 修改文件：`src/drone_bringup/package.xml`、`src/drone_bringup/CMakeLists.txt`、`src/drone_bringup/src/flight_node.cpp`

## 一、阶段一：修复编译

### 1.1 报错：catkin 依赖声明不一致

#### 现象

```text
CMake Error at src/drone_bringup/CMakeLists.txt:10 (catkin_package):
  the catkin package 'geometry_msgs' has been find_package()-ed but is
  not listed as a build dependency in the package.xml
```

#### 原因

`CMakeLists.txt` 第 10 行的 `catkin_package(CATKIN_DEPENDS roscpp geometry_msgs std_msgs)`
以及前面的 `find_package()` 都用到了 `geometry_msgs` 和 `std_msgs`，但 `package.xml`
里只声明了 `roscpp` 和 `drone_backend`。

catkin 会强制校验下面这三处声明是否自洽：

- `package.xml` 的 `<build_depend>` 和 `<exec_depend>`：声明这个包需要什么依赖；
- `CMakeLists.txt` 的 `find_package()`：让编译器、链接器真的找到头文件和库；
- `CMakeLists.txt` 的 `catkin_package(CATKIN_DEPENDS ...)`：告诉依赖自己的下游包也需要这些依赖。

三处缺任何一处，catkin 就拒绝配置。这个设计是为了避免「本机靠残留环境编译通过、换台机器就崩」。

#### 修改

在 `package.xml` 中补充 4 行：

```xml
  <build_depend>geometry_msgs</build_depend>
  <build_depend>std_msgs</build_depend>

  <exec_depend>geometry_msgs</exec_depend>
  <exec_depend>std_msgs</exec_depend>
```

这里分开写 `build_depend` 和 `exec_depend`，而不是用 `<depend>` 简写，是为了和文件里已有的写法保持一致。

### 1.2 编译目标指向不存在的文件

#### 现象

这一处没有出现在编译输出里。

第一次 `catkin_make` 时，catkin 在 `catkin_package()`（第 10 行）就中止了配置，
第 14 行的 `add_executable()` 根本没被执行到，所以终端里看不到与它相关的报错。
问题是修完 1.1 之后、逐行读 `CMakeLists.txt` 时发现的：第 14 行指向了
`src/example_listener.cpp`，而 `src/` 目录下实际只有 `flight_node.cpp`。

如果只修 1.1 就重新编译，这里会立刻报：

```text
CMake Error at src/drone_bringup/CMakeLists.txt:14 (add_executable):
  Cannot find source file:

    src/example_listener.cpp
```

#### 原因

`CMakeLists.txt` 最后两行指向了 `src/example_listener.cpp`，但 `src/` 目录下实际只有
`flight_node.cpp`，这个源文件根本不存在。同时 `launch/mission.launch` 里写的是
`<node type="flight_node" .../>`，所以产物名也必须是 `flight_node`。

#### 修改

```cmake
# 修改前
add_executable(example_listener src/example_listener.cpp)
target_link_libraries(example_listener ${catkin_LIBRARIES})

# 修改后
add_executable(flight_node src/flight_node.cpp)
target_link_libraries(flight_node ${catkin_LIBRARIES})
```

#### 理解

`add_executable(产物名 源文件)` 两个参数的含义：

- 第一个参数是编译出来的可执行文件叫什么。它必须和 launch 文件里 `<node type="...">`
  的值完全一致，否则 `roslaunch` 会报 `cannot locate node`；
- 第二个参数是用哪个源文件编译，必须是真实存在的路径。

`target_link_libraries` 的第一个参数必须和 `add_executable` 的产物名同名。

改完后 `catkin_make` 输出 `[100%] Built target flight_node`，阶段一完成。

## 二、阶段二：起飞与避障

阶段二的现象不是编译错误，而是程序能跑但行为不对。第一次运行时后端日志：

```text
[WARN] 消息头不合法（时间戳为 0）
[INFO] [状态] 高度=0.00  距离=2.00  链路=失效
[ERROR] 阶段二超时：没有完成起飞并避开障碍
```

三个症状分别对应 `flight_node.cpp` 里的不同位置。

### 2.1 消息头时间戳为 0 导致链路失效

#### 现象

后端持续报 `消息头不合法（时间戳为 0）`，状态里 `链路=失效`，飞机完全不动。

#### 原因

```cpp
setpoint.header.stamp = ros::Time();
```

`ros::Time()` 的无参构造是纪元零点（0 时刻），不是当前时刻。带时间戳的消息里塞 0，
接收方（这里是后端）会判定为「未初始化或无效」并直接丢弃，所以链路一直显示失效。

#### 修改

```cpp
setpoint.header.stamp = ros::Time::now();
```

同属「消息根本发不出去」的还有两处，虽然报错形式不同：

```cpp
// 1 Hz 的循环不满足 500 ms 心跳要求（500 ms 意味着至少 2 Hz）
ros::Rate rate(1.0);   →   ros::Rate rate(20);

// 发的是从未赋值的 fakepoint，前面填的 setpoint 全部白填
g_setpoint_pub.publish(fakepoint);   →   g_setpoint_pub.publish(setpoint);
```

### 2.2 高度一直是 0.00

#### 原因

`setpoint.pose.position.z` 被填成 `0.0`，而任务要求飞到 1.5 m。再叠加 2.1 里的
`publish(fakepoint)` 问题，等于发出去的目标 x、y、z 全是 0。

#### 修改

```cpp
setpoint.pose.position.z = 1.5;
```

改完后端日志出现 `高度=0.53 → 0.83 → 1.14 → 1.45 → 1.50`，高度稳定在 1.5 m。

### 2.3 距离恒为 2.00，飞机不降落

#### 现象

后端日志里 `距离=2.00` 一直不变，飞机飞到 1.5 m 后一路往前，直到超时。

#### 原因

```cpp
ros::Subscriber obstacle_sub = nh.subscribe("/drone", 10, obstacle_cb);
```

话题名写错了。后端实际发布在 `/drone/sensor/obstacle_distance`（类型 `std_msgs/Float32`），
订阅 `"/drone"` 这个话题并不存在，回调 `obstacle_cb` 从未被调用过，所以 `distance`
一直停留在初始化值 `2.0`。

#### 修改

```cpp
ros::Subscriber obstacle_sub = nh.subscribe(
    "/drone/sensor/obstacle_distance", 10, obstacle_cb);
```

#### 这一处是整关最值得记的教训

ROS 里话题名错一个字符，程序不会报任何错：节点照常启动、照常发消息、照常打印日志，
只是回调永远不触发、数据永远是初始值。

这类「静默失效」只能靠观察系统状态来定位：

```bash
rostopic list                                  # 看实际存在哪些话题
rostopic list | grep -i obstacle               # 过滤关键词
rostopic echo /drone/sensor/obstacle_distance  # 看有没有数据在流动
rostopic info /drone/setpoint                  # 看话题类型、谁在发、谁在收
rqt_graph                                      # 图形化看节点和话题的连接
```

其中 `rqt_graph` 最直观：如果 `flight_node` 和 `sensor_node` 之间没有连线，说明订阅名一定不对。

结论是：调试 ROS 时要优先向系统查事实，而不是靠改代码猜。

### 2.4 降落阈值

任务要求距离障碍小于 0.5 m 时降落。

```cpp
if (distance < 0.0)   →   if (distance < 0.5)
```

这段代码的逻辑要注意：判断用的是 `distance`（由回调异步写入），改的是
`setpoint.pose.position.z`。两者不是同一个变量。而且 2.3 的话题名如果不对，
`distance` 永远是 2.0，这个 `if` 永远不会成立。

## 三、环境操作踩坑

下面四条都不是代码问题，但实际卡住的时间比写代码长，一并记录。

### 3.1 Unable to communicate with master

执行 `rostopic`、`rosnode` 这类命令时报这个错，原因是 `roscore` 没有运行。
所有节点向 master 注册，所有 `rostopic` 命令向 master 查询，master 不在就没有响应。

排查入口：

```bash
rosnode list      # 报同样的错，就说明 master 没起
```

正常流程下 `./run_sim.sh` 会自动起 master。如果后端因超时退出，master 也跟着关掉，
此时再执行 `rostopic` 必然报错。

### 3.2 package 'drone_backend' not found

新开的终端里执行 `./run_sim.sh` 报这个错。原因是 `source` 只对当前终端进程生效，
新终端没有加载过工作空间环境。

`~/.bashrc` 里的内容是系统级的（ROS 本体、PX4、Gazebo），每次开终端自动生效；
而工作空间的 `setup.bash` 不在 `.bashrc` 里，不会自动加载。

### 3.3 mission.launch is neither a launch file in package

这时 `roslaunch` 找不到自己的包。原因是只 `source` 了 `install/setup.bash`，
没有 `source devel/setup.bash`。

### 3.4 install 与 devel 是两个独立空间

- `install/`：仓库自带的预编译后端 `drone_backend`，包括后端节点和自定义消息 `DroneState`。
  跑后端的终端、以及用到该消息的终端，需要 source 它。
- `devel/`：自己编译出来的 `drone_bringup` 和 `flight_node`。跑自己节点的终端，需要 source 它。

两个空间互不包含。都要用时先 `install` 再 `devel`，因为 `devel` 的 setup 会重写
`ROS_PACKAGE_PATH`，必须放在后面。

一个值得养成的习惯：启动前先用 `rospack find` 验证，而不是靠记忆。

```bash
rospack find drone_backend     # 终端 1 必须有输出
rospack find drone_bringup     # 终端 2 必须有输出
```

### 3.5 注意事项：改了 .cpp 必须重新 catkin_make

这一条不是踩过的坑，而是后续必须遵守的规则，所以单独记下来。

`roslaunch` 运行的是 `devel/lib/drone_bringup/flight_node` 这个编译产物，不是源文件。
改了源码不重新编译，跑的就永远是旧程序，很容易误判成「我明明改了啊」。

作为对比：第二关的 `.yaml` 参数文件改了不需要重新编译，因为它是运行时读取的。

## 六、收获总结

1. 包的依赖声明必须三处自洽：`package.xml`、`find_package()`、`catkin_package(CATKIN_DEPENDS)`。
   CMake 的报错通常已经把答案写出来了，关键是读懂它在指责哪个文件的哪一行。

2. `add_executable(产物名 源文件)` 有两个约束：产物名必须和 launch 里 `type` 一致，
   源文件必须真实存在。它们分别对应「roslaunch 找不到节点」和「CMake 找不到源文件」两类报错。

3. `ros::Time()` 不等于现在。带时间戳的消息（`PoseStamped`、传感器数据、tf 变换）里填 0
   会被接收方判为无效。取当前时间要用 `ros::Time::now()`。

4. ROS 最难的 bug 是静默失效：话题名、消息类型、时间戳任一项不对，程序都不报错，
   只是数据不流动。所以要养成用 `rostopic list`、`rostopic echo`、`rqt_graph` 观察系统状态的习惯，
   先说清「现在系统里有什么」，再动代码。

5. `source` 是进程级、一次性的。每个新终端都要重新加载；`install` 与 `devel` 是两个独立空间，
   都要用时按 install 到 devel 的顺序。`rospack find` 是验证环境是否加载的最快手段。

6. ROS 的调试思路是「先观察，再推理，最后才改代码」。这一关出的每一个问题都能在终端输出里
   找到线索，没有需要凭感觉猜的地方。

## 七、附：讲义「2.3 你可能需要了解」的思考题

### 7.1 两行 source 分别在做什么

讲义的原文是 `source /opt/ros/noetic/setup.zsh` 和 `source ~/airhust_ws/devel/setup.zsh`。
本机默认 shell 是 bash，所以实际执行的是对应的 `.bash` 版本，内容等价。

第一行，加载 **ROS 本体环境**。

它设置的是系统安装的 ROS Noetic 这一套环境变量：

- `ROS_ROOT`、`ROS_PACKAGE_PATH`：让系统知道 `/opt/ros/noetic/share` 下面有哪些官方包；
- `PATH`：让 `rosrun`、`roslaunch`、`rostopic`、`catkin_make` 这些命令可以直接调用；
- `PYTHONPATH`、`LD_LIBRARY_PATH`、`CMAKE_PREFIX_PATH`：让 Python 能 import rospy，
  让编译和运行时能找到 ROS 的库，让 CMake 能 `find_package` 到 catkin。

不执行它，终端里根本不存在 ROS 这个概念，`rosrun` 会报 command not found。

第二行，加载 **自己的工作空间环境**。

`devel/setup.bash` 是 `catkin_make` 生成的，作用是把自己编译出来的东西挂到同一批变量上：

- 把 `~/airhust_ws/devel` 追加进 `ROS_PACKAGE_PATH`，这样 `rosrun`、`roslaunch`
  才能找到您自己的包；
- 追加进 `CMAKE_PREFIX_PATH`，这样别的包能 `find_package` 到您生成的消息头文件；
- 追加进 `LD_LIBRARY_PATH` 和 `PYTHONPATH`，让运行时的动态库和 Python 模块能被找到。

**为什么讲义说「初始无 devel 目录，可尝试先编译一次」**

因为 `devel/` 是编译的产物，第一次 `catkin_make` 之前它根本不存在，此时 `source` 它会报
`No such file or directory`。

而 `catkin_make` 本身不依赖 `devel/setup.bash`，它只需要 `/opt/ros/noetic` 里的 catkin
（由第一行提供）。所以正确顺序是：先 source 本体，再编译，编译完才有 devel 可以 source。

**两者的关系**

第一行是「系统里装了什么」，第二行是「我自己造了什么」。后者必须在前者之后加载，
因为 catkin 生成的脚本会基于当前的 `CMAKE_PREFIX_PATH` 重新计算环境，前提是本体的变量已经就绪。

**为什么每个新终端都要重来一遍**

`source` 修改的是**当前这个 shell 进程**的环境变量，不是系统配置。开新终端就是一个干净的新进程，
变量全部回到 `.bashrc` 里的初始状态。`.bashrc` 只有 ROS 本体那几行，没有工作空间的行，
所以工作空间环境必须每次手动加载。

### 7.2 CMakeLists.txt 和 package.xml 的作用

**package.xml 是包的身份证加依赖清单。**

它声明的是「这个包是什么、需要什么」：

- 元信息：包名、版本、描述、作者、许可证。`rospack find`、`roslaunch` 认包靠的就是它；
- 依赖声明：`<buildtool_depend>`（构建工具，通常只有 catkin）、`<build_depend>`
  （编译期需要）、`<exec_depend>`（运行期需要）、`<test_depend>`。
- 这些声明会被 `rosdep` 用来一键安装系统依赖，也会被 catkin 用来校验依赖完整性。

它本身**不参与编译**，是一份纯声明文件。

**CMakeLists.txt 是包的构建脚本。**

它说明的是「具体怎么编译」：

- `find_package()`：找出依赖包，拿到它们的头文件路径和库；
- `catkin_package()`：声明本包对外导出什么（`CATKIN_DEPENDS`、`INCLUDE_DIRS`、`LIBRARIES`），
  供依赖本包的下游包使用；
- `add_message_files()` / `generate_messages()`：把 `.msg`、`.srv` 编译成 C++ 和 Python 头文件；
- `add_executable()` / `target_link_libraries()`：生成可执行文件并链接依赖库；
- `install()`：定义安装规则。

**两者为什么必须一致**

`package.xml` 是「声明」，`CMakeLists.txt` 是「执行」。声明了才能用，用了就必须声明。

第一次编译报的 `geometry_msgs ... has been find_package()-ed but is not listed as a build
dependency`，本质就是「执行」里用了「声明」里没有的东西，catkin 拒绝继续。这个强校验是
故意的：放任不一致，就会出现「在这台机器上能编译、换台机器就崩」的隐蔽问题。

一句话对比：**package.xml 说需要什么，CMakeLists.txt 说怎么用这些去构建。**

### 7.3 ROS 的文件层级概念

从外到内分四层。

**第一层：工作空间（workspace）**

`~/airhust_ws` 就是工作空间，标准的四个子目录各司其职：

- `src/`：放源码包，是**唯一需要手动管理**的目录；
- `build/`：CMake 的中间产物（缓存、Makefile），删掉不影响源码；
- `devel/`：开发空间，编译出来的可执行文件、库、生成的消息头文件，以及 `setup.bash` 都在这里。
  可以删，重新编译会再生成；
- `install/`：安装空间，`catkin_make install` 或配置 `--install` 时才生成，是可以直接分发的成品。

第一关还有个特殊情况：`install/` 里放的是仓库自带的**预编译后端** `drone_backend`，
不是自己编译出来的，所以它和 `devel/` 是两套互不包含的内容。

**第二层：包（package）**

包是 ROS 的组织单位，也是一个能被单独编译、单独发布的最小单元。
判定标准是目录里必须有 `package.xml`（`format="2"` 时还要求有 `CMakeLists.txt`），
两者齐备，`rospack` 和 `catkin` 才认它是一个包。

包内常见的标准子目录：

- `src/`：C++ 源文件
- `include/`：头文件
- `scripts/`：Python 脚本
- `launch/`：`.launch` 启动文件
- `msg/`、`srv/`、`action/`：自定义消息、服务、动作的定义
- `config/`：YAML 参数文件
- `urdf/`：机器人模型描述

这些目录名是**约定俗成**，不是强制的。编译器只认 `CMakeLists.txt` 里写的路径，
但遵循约定能让别人一眼看懂您的包。

**第三层：消息、服务、节点、launch**

这些是包内部的组成单元：

- 节点（node）是可执行程序，编译后在 `devel/lib/<包名>/` 下；
- 消息（`.msg`）定义话题的数据结构，编译后生成 C++ 头文件和 Python 模块，
  第二关会用到的 `DroneState` 就是这种；
- launch 文件（`.launch`）是启动脚本，用 XML 描述「同时启动哪些节点、用什么参数、放什么命名空间」。

**第四层：坐标系、命名空间这类运行期概念**

属于运行时才存在的逻辑结构，和文件系统无关，后面几关会用到。

**查找链条**

`rosrun <包名> <可执行文件名>` 和 `roslaunch <包名> <文件名>.launch` 的定位过程是：

1. 在 `ROS_PACKAGE_PATH` 列出的每个目录里，找名字匹配的包；
2. 找到了包，再看包内有没有对应的可执行文件或 `launch/` 目录下的文件。

这就解释了另外两类报错：

- `package 'drone_backend' not found`：第 1 步失败，`ROS_PACKAGE_PATH` 里没有这个包，
  说明对应的 `setup.bash` 没 source；
- `[mission.launch] is neither a launch file in package [drone_bringup]`：第 2 步失败，
  包在 `install/` 里但不在 `devel/` 里，说明 `devel/setup.bash` 没 source。

**一句话总结层级关系：工作空间包含包，包包含节点、消息、launch 和配置。**
