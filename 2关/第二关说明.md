## 一、个人副本中的代码与配置

```bash
cd ~/airhust_tutorial2026_ws/2*/airhust_tutorial26_template
```


`source devel/setup.bash` 不能省。`.bashrc` 里 source 的是第一关的工作空间，不 source 会报 `package 'template' not found`。

### 1.2 实际参数

`src/template/config/template.yaml`：

```yaml
err_max: 0.15
if_debug: 1
circle_radius: 1.5
circle_num: 12
circle_center_x: 0.0
circle_center_y: 2.0
```

前两个是模板自带，后四个是本任务新增：

- `circle_radius`：圆周半径，米
- `circle_num`：一圈分成的航点段数，无量纲
- `circle_center_x`、`circle_center_y`：圆心坐标，米，相对起飞点

`circle_num` 取 12 是按误差推的：半径 1.5 时相邻航点间距约 `2π × 1.5 / 12 ≈ 0.78 m`，远大于 `err_max`（0.15），不会出现“刚到一个点就同时满足下一个点”的跳点。

`circle_center_y` 取 2.0 是为了让圆心离起飞点远一点，避免飞机在原点正上方打转。

### 1.3 改动清单（五处）

**（1）`template.yaml`**：见 1.2，新增四个绕圈参数。

**（2）`template.cpp` 全局变量区**：

```cpp
float circle_radius = 1.5;
float circle_num = 12;
float circle_center_x = 0.0;
float circle_center_y = 0.0;
int circle_index = 0;
```

**（3）`template.cpp` 的 `main` 里读取参数**（放在 `nh.param<float>("err_max", ...)` 那两行下面）：

```cpp
nh.param<float>("circle_radius", circle_radius, 1.5);
nh.param<float>("circle_num", circle_num, 12);
nh.param<float>("circle_center_x", circle_center_x, 0.0);
nh.param<float>("circle_center_y", circle_center_y, 0.0);
```

**（4）`template.cpp` 的 case 2 与 case 3**：

case 2 原来飞到 `(4, 0)`，改成飞到圆周起点 `θ = 0` 处，即 `(cx + r, cy)`，机头朝切向 `π/2`（朝 `+y`）：

```cpp
case 2:
{
  if (mission_pos_cruise(circle_center_x + circle_radius, circle_center_y, ALTITUDE, M_PI / 2.0, err_max))
  {
    circle_index = 0;
    mission_num = 3;
  }
  break;
}
```

case 3 原来是相对位移，改成按离散航点逐个推进：

```cpp
case 3:
{
  float theta = 2.0 * M_PI * circle_index / circle_num;
  float tx = circle_center_x + circle_radius * cos(theta);
  float ty = circle_center_y + circle_radius * sin(theta);
  float target_yaw = theta + M_PI / 2.0;
  if (mission_pos_cruise(tx, ty, ALTITUDE, target_yaw, err_max))
  {
    circle_index++;
    if (circle_index > circle_num)
    {
      circle_index = 0;
      mission_num = 4;
    }
  }
  break;
}
```

坐标系说明：`mission_pos_cruise()` 内部会给传入的 x、y、z 加上记录的起飞点偏移（`init_position_x_take_off` 等），所以这里填的圆心和半径都是**相对起飞点**的世界系坐标，和 `local_pos` 的参考系一致。这一点必须对齐，否则圆会整体偏移一个起飞点的距离。

case 1、case 4、case 5 没有改动，分别是起飞、悬停 3 秒、降落。

**（5）`template.h` 的到达判定**（第二版加切向朝向后必须改）：

原来直接比较两个角度：

```cpp
fabs(yaw - target_yaw) < 0.1
```

改成先算误差、再把误差折到 `[-π, π]`：

```cpp
double dyaw = target_yaw - yaw;
while (dyaw > M_PI)  dyaw -= 2.0 * M_PI;
while (dyaw < -M_PI) dyaw += 2.0 * M_PI;
```

判定改为 `fabs(dyaw) < 0.1`。

这个改动对所有 case 都安全：误差本来就在 `[-π, π]` 内时，两个 `while` 一次都不执行，行为和原来完全一致。

## 二、一次完整演示

### 2.1 从启动到降落的流程

```
启动 → 请求 OFFBOARD + 解锁，持续发布目标 → 高度到位后 break
     → case 1 起飞到 (0, 0, 0.8)
     → case 2 飞到圆周起点 (cx + r, cy)，机头 π/2
     → case 3 按 θ_k = 2πk/N 逐点推进，走满 13 个目标点
     → case 4 悬停 3 秒
     → case 5 降落并等 5 秒
```

Gazebo 里看到的动作是：起飞爬升到 0.8 m，向前飞到圆周起点，然后一边绕圈一边调整机头方向（机头始终朝切线），走满一圈回到起点上方，悬停 3 秒，垂直下降落地。

第二版加了切向朝向后，动作是“飞一段、停一下等机头转、再飞下一段”，不是平滑滑过。这个现象在 3.5 里有量化分析。

### 2.2 用日志说明绕圈进度

终端输出里判断进度的三个标志：

- `mission_num = 3` 首次出现 → 开始绕圈
- `mission_num = 4` 出现 → 一圈结束，进入悬停
- `Hovering at (x, y, z)` → 悬停开始，这个坐标同时用来验证闭合

一次实际运行的日志：

```
[INFO] [1795069840.999392879, 85.528000000]: mission_num = 3
[INFO] [1795069861.207939514, 105.528000000]: mission_num = 4
[INFO] [1795069861.207984520, 105.528000000]: Hovering at (1.59, 1.88, 0.64) for 0.35 seconds
```

`hover()` 会持续打印已悬停的秒数，从 0.35 一直数到 3.00，到 3.00 后返回 true 进 case 5。

**闭合的判断**：理论起点是 `(1.5, 2.0)`，实际悬停位置 `(1.59, 1.88)`，x 差 0.09、y 差 0.12，都在 `err_max` 以内，说明最后一格真的飞回来了。

**耗时的读法**：`105.528 − 85.528 = 20.0` 秒。

z 是 0.64，比 `ALTITUDE`（0.8）低 0.16。原因是位置控制的到达判定有 0.15 的容差，一进入容差就认为到位、不再往上修；`hover()` 记录的又是到位之后又漂了一下的实际位置，所以看起来“沉”了一点。这是容差导致的，不是高度在持续漂移。

## 三、方案说明

### 3.1 选择了什么方法，为什么

选讲义思路 A（离散航点）：`θ_k = 2πk/N`，每到一个点再算下一个。

三种思路的取舍：

- **思路 A 离散航点**：到达判定可以直接复用 `mission_pos_cruise()` 的返回值，不需要额外写判断逻辑，改动量最小。
- **思路 B 时间参数化**：目标点随时间连续移动，`θ(t) = θ0 + ω(t − t0)`。“是否到达”变得没有意义——目标一直在动，返回值不能直接用来推进，必须自己设计完成判断。第一版不引入这个复杂度。
- **思路 C 前方视角**：用实际位置反算当前角度，再往前看 δ。轨迹最贴合实际运动，但要处理角度跨越 ±π 的问题，还要单独记录“已经绕了多少”，复杂度最高。

### 3.2 怎样确认数据就绪

跑之前固定三步：

```bash
rosparam load src/template/config/template.yaml
rosparam list | grep circle
rosparam get /circle_radius
```

`rosparam get` 必须返回设定值。如果返回 `Parameter [/circle_radius] is not set`，说明参数没进服务器，**这时不能继续往下跑**。

原因是 `nh.param` 的第三个参数是兜底值，只在键不存在时才生效。忘了 load，`err_max` 会取到默认值 0，于是“位置误差小于 err_max”永远不成立，飞机会正常起飞、正常飞过去，然后停在目标点上方不动，`mission_num` 一直刷 2，**不报任何错**。

状态方面，`local_pos` 的更新依赖 `ros::spinOnce()`，`nh.subscribe` 只是登记回调、本身不触发调用。如果回调没被触发，`local_pos` 会一直停在旧值，程序同样不报错、只是行为静止。

### 3.3 怎样判断绕圈完成

`circle_index` 从 0 开始，每到一个点加 1，条件是 `circle_index > circle_num` 才进 case 4。

推一遍取值：

- 进入 case 3 时 `circle_index = 0`，`θ = 0`，这个点就是 case 2 已经到达的起点，所以**第一轮立刻返回 true，不移动、不耗时**，`circle_index` 变 1
- 之后走 `k = 1..11`，对应 `θ = 30°` 到 `330°`
- 如果写 `>=`：`k = 11` 到达 330° 后 `circle_index` 变 12，`12 >= 12` 成立，任务结束。**结果是圆缺最后 30° 的弧，是开口的**
- 如果写 `>`：`k = 12` 时 `θ = 2π`，目标回到起点，飞机飞完最后一段弧、回到起点上方，才 `13 > 12` 成立，进 case 4。**圆是闭合的**

所以实际是“13 个目标点、12 段弧”：`k = 0` 那格是白给的，`k = 12` 那格负责闭合。这也解释了为什么 case 2 的目标 yaw 要设成 `π/2` 而不是 0——如果 case 2 用 0，`k = 0` 这格就要先原地转 90°，反而变成最慢的一段。

闭合可以用 case 4 打印的坐标验证，见 2.2。

### 3.4 调试中遇到的问题

#### 一、角度绕圈：

**这个不是运行时撞到的，是加切向朝向之前先算出来的。** 说明一下推演过程

|                                   |                  |                                                                                                                                                                                                                  |
| --------------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mission_pos_cruise()` 的到达条件里有 \` | yaw − target_yaw | < 0.1`，`yaw`来自`getRPY()`，范围是 `[-π, π]`；而 `target_yaw = θ + π/2`会随`θ`一直增大到`2π + π/2`。取 `θ = 210°`：`target_yaw = 5.24`，飞机实际 yaw 已回绕成 `−1.05`，`fabs(−1.05 − 5.24) = 6.29`，永远大于 0.1。位置早就到了，`mission_num\` 却不动，而且不报错。 |

所以第一版干脆固定 yaw = 0，先把圆画出来；确认圆闭合之后，第二版再加切向，同时把判定改成折误差：

```cpp
double dyaw = target_yaw - yaw;
while (dyaw > M_PI)  dyaw -= 2.0 * M_PI;
while (dyaw < -M_PI) dyaw += 2.0 * M_PI;
```

**关键判断：为什么归一化误差而不是归一化目标。** 只把 `target_yaw` 折到 `[-π, π]` 是没用的：折完之后，当飞机实际朝向在 `+179°`、目标在 `−179°` 时，两个数看起来差了 358°，物理上其实只差 2°，问题只是从一处换到另一处出现。两个角度之差的物理意义本来就是周期性的，所以必须折误差。

这个改动对所有 case 都安全：误差本来就在 `[-π, π]` 内时，两个 `while` 一次都不执行，行为和原来一致。

**副作用**：到达变得更难。现在要求位置到位**并且**机头偏差小于 0.1 rad（约 5.7°），两个条件同时满足的窗口变窄，整圈耗时明显增加，量化见 3.5。

#### 二、电机不转：

**现象**：有一次运行，程序已经进到 case 1 并在持续发 `(0, 0, 0.8, 0)` 的目标，但飞机趴在地面、电机完全不转，程序这边没有任何报错。

**判断方法**：看 `/mavros/state` 里的 `armed` 字段，同时注意 PX4 终端里只有 `Preflight Fail` 而没有 `Armed`/`Taking off`。三个信号合起来就是“没解锁”，而不是“控制算错了”。

**原因推测**：前一次运行是 `exit(0)` 直接退出的，没有 disarm，PX4 内部状态和实际不一致，导致后续解锁请求被拒。这条和附录 A 里那个 failsafe 是同一个根源。

**处理**：重启整个仿真（`Ctrl+C` 掉 `roslaunch` 再重新起），然后重新 `load` 参数、重新运行节点，问题消失。

### 3.5 一次失败的预测与数据反解

改动前先做了预测：半径从 1.0 改成 1.5，周长变 1.5 倍，如果平均速度不变，耗时应该是 27 秒。

实测只有 20.0 秒，**预测错了**。错的原因是“平均速度不变”这个前提不成立。

两组数据：

**半径 1.0**

- 绕圈耗时：`266.812 − 248.812 = 18.0` 秒
- 悬停位置：`(1.05, 1.88, 0.69)`，起点理论值 `(1.0, 2.0)`，误差 `(0.05, 0.12)`

**半径 1.5**

- 绕圈耗时：`105.528 − 85.528 = 20.0` 秒
- 悬停位置：`(1.59, 1.88, 0.64)`，起点理论值 `(1.5, 2.0)`，误差 `(0.09, 0.12)`

两次都闭合，误差都在 `err_max` 以内。

周长多了 3.14 m，时间只多了 2.0 秒。设每段固定开销为 `a`、飞行速度为 `v`，两点定一条线：

```
12a + 6.28/v = 18.0
12a + 9.42/v = 20.0
```

两式相减得 `3.14/v = 2.0`，即 `v ≈ 1.57 m/s`（正好接近 PX4 默认的水平限速）。代回第一式：`12a = 18.0 − 6.28/1.57 ≈ 18.0 − 4.0 = 14.0`，即 **每个航点约 1.17 秒的固定开销**。

也就是说，12 个航点里约 14 秒是“等”，真正飞行只有 4 到 6 秒。这些等待主要花在等机头转到切向。

这个模型还能推出一个反直觉的结论：**增加 `circle_num` 会让圆更平滑，但总耗时会变长**，因为固定开销按点数线性增长，而飞行时间只随周长增长。想让它变快，该动的是 yaw 容差或到达判定，不是点数。

按这个模型估算，把 yaw 容差从 0.1 放宽到 0.2，每点等待约减半，总耗时应该在 12 到 13 秒。这一组对照实验还没做，留作下一步。

## 四、短练习：从“去哪里”到“怎样移动”

这一节是推演，尚未在仿真中实测。目的是把“位置控制”换成“速度控制”后，每个环节要想清楚什么。

### 4.1 要填哪些字段，掩码怎么算

位置控制告诉飞控“希望到这个坐标”，速度控制告诉它“沿某个方向、以多大速度走”。字段从 `position` 换成 `velocity`，掩码也必须跟着改。

```cpp
setpoint_raw.type_mask = 1 + 2 + 4 + 64 + 128 + 256 + 2048;   // 即 2503
setpoint_raw.coordinate_frame = 1;
setpoint_raw.yaw = 0.0;

setpoint_raw.velocity.x = /* 本轮 vx */;
setpoint_raw.velocity.y = /* 本轮 vy */;
setpoint_raw.velocity.z = 0.0;
```

逐位对照：

- 加了 `1 + 2 + 4`：忽略位置 x/y/z
- 加了 `64 + 128 + 256`：忽略加速度
- 加了 `2048`：忽略 yaw_rate
- **没加** `8 + 16 + 32`：vx/vy/vz 生效
- **没加** `1024`：yaw 生效
- 没加 `512`：三个加速度/力字段都被忽略，力模式用不上

一句话：关掉位置和加速度，只留速度和朝向。

`coordinate_frame` 仍是 1，和原来的位置控制一致，所以 `velocity.x` 的正方向和 `position.x` 的正方向是同一个方向，都是世界系，**不是机头前后**。机头朝哪都不影响。

`velocity.z` 必须显式写 0。“目标竖直速度为 0”表示保持当前高度。注意速度控制下没有绝对高度闭环，飞久了会缓慢掉一点。

### 4.2 从位置算速度

每轮用实时位置算误差，再乘比例系数：

```cpp
float ex = target_x - local_pos.pose.pose.position.x;
float ey = target_y - local_pos.pose.pose.position.y;
float vx = k * ex;
float vy = k * ey;
```

`k` 取 `0.5` 起步。三个点可以验算一下：目标 2、当前 0，误差 2，`vx = 1`；当前 1.8，误差 0.2，`vx = 0.1`；当前 2.1，误差 −0.1，`vx = −0.05`。

第三行是关键：**超过目标后误差变负，速度自动反向**，这就是比例控制比“发固定速度”强的地方。

### 4.3 限速：限合速度，不是限分轴

`v = k·e` 在远距离会算出离谱的速度：误差 10 米、`k = 0.5`，就是 5 m/s。必须限。

**分轴限幅**（对三轴各做 `if (vx > vmax) vx = vmax;`）有两个问题：x、y 都取到上限时合速度是 `√2 × vmax`，斜着飞会超速；而且限幅只压低分量，方向也被改变了。

**合速度限幅**才对：

```cpp
float vnorm = sqrt(vx * vx + vy * vy);
if (vnorm > v_max && vnorm > 1e-6)
{
  float s = v_max / vnorm;
  vx *= s;
  vy *= s;
}
```

按比例缩放，方向不变、模长压到 `v_max`。`v_max` 取 `0.5`，和 `k = 0.5` 配合，误差 1 米以内不会触发限速。

`vnorm > 1e-6` 这个判断是因为误差恰好为 0 时会除以 0 得到 `inf`，速度指令变成非法值，PX4 会报 `invalid setpoints`。


### 4.4 到达后怎样停止

```cpp
if (fabs(ex) < err_max && fabs(ey) < err_max && fabs(ez) < err_max && fabs(dyaw) < 0.1)
{
  setpoint_raw.velocity.x = 0.0;
  setpoint_raw.velocity.y = 0.0;
  setpoint_raw.velocity.z = 0.0;
  publish(setpoint_raw);
  return true;
}
```



另外，缩小 `err_max` 的效果要说清楚：它不会让轨迹更精确，只会让飞机更晚才“认定到了”。因为 `v = k·e` 越接近目标越慢，容差设太小会出现“最后几厘米磨很久”的现象，时间明显变长，轨迹并不会更好看。

### 4.5 这段逻辑放在哪

放在 **case 内部、每轮循环都执行的位置**。20 Hz 每轮做一遍：读最新位置、算误差、算速度、限幅、publish、判到达。

不能写在 `main` 开头算一次，也不能放在 `switch` 外面。

具体落点：这一版把它放在 **case 2 内部**，也就是“飞向圆周起点”这一段。练习本身要求的就是“接近一个目标点并停下”，case 2 正好是一个天然的目标点；到位后进 case 3 绕圈，互不影响。

要注意的是，case 2 的目标 yaw 是 `π/2`，而掩码里 yaw 位没被忽略，所以**姿态仍然是位置式的**，速度控制只管平移，机头还是按 `yaw` 字段转。两者不冲突。

### 4.6 预测：速度只算一次会怎样

问题在**速度不衰减**：速度定死之后，飞机不按“远快近慢”的规律减速，而是匀速直冲。`v = k·e` 的全部意义就是靠误差变小来自动减速，只算一次就把这个机制废掉了。

**具体现象取决于“只算一次”把哪一部分搬到了循环外面**，两种写法结果不同：

**情形一：整块只执行一次（算速度和判到达都在循环外）**

起始误差 2 米、`k = 0.5`，算出 1 m/s，此后不再改变。飞机以 1 m/s 匀速直飞，冲过目标点还是 1 m/s，最后撞墙或飞出视野。

判定也只在开头跑过一次，那时误差还是 2 米，返回 false，之后再没判过，所以不会有任何“到了”的动作。**结果是匀速直线飞出去。**

**情形二：只有算速度那一行在循环外，判定仍在循环里**

速度仍是固定的 1 m/s，但判定每轮都用实时位置跑。飞机冲过目标时，位置误差在穿过目标那一瞬间小于 `err_max`，判定返回 true。如果代码在这里置零速度，现象是**过冲之后急停**——冲出几十厘米，然后停在目标外侧。

它不会飞出去，但也绝不是“停在目标上”。

**所以结论分两层**：不变的是“速度不衰减、没有减速过程”；取决于代码结构的是“飞出去”还是“过冲急停”。判定本身没有失效，失效的是“用误差驱动速度”这个反馈环节。

这里要特别区分**哪个东西被冻结了**。`local_pos` 这个变量本身永远在更新，只要 `ros::spinOnce()` 在循环里执行，回调每收到一帧消息就改写它，它一直是新鲜的。被冻结的是**由它算出来的速度**：`float vx = k * ex;` 这一行如果写在循环外面，就只执行一次，`vx` 定死成那个数，之后 `local_pos` 再怎么变也没人拿它重新乘 `k`。

用代码看得最清楚：

```cpp
float vx = k * (tx - local_pos.pose.pose.position.x);   // 在 while 外面，只算一次
while (ros::ok())
{
  float ex = tx - local_pos.pose.pose.position.x;       // 每轮重读，永远新鲜
  if (fabs(ex) < err_max) { /* 到达，置零并发布 */ }
  setpoint_raw.velocity.x = vx;                         // 却永远是那个旧值
  ros::spinOnce();
}
```

一句话：`local_pos` 的新鲜度由 `spinOnce()` 决定，`vx` 的新鲜度由**它写在哪**决定——写进循环体就新鲜，写在循环外就冻结。

这也说明 `v = k·e` 必须每轮重算的根本原因：它靠误差变小来实现自动减速，而误差来源必须是实时位置。

## 附录 A　已知不足

- **退出流程不完整**：任务最后 `exit(0)` 直接结束进程，`/mavros/setpoint_raw/local` 立刻断流，PX4 在 OFFBOARD 模式下不允许目标流中断，于是刷 `Failsafe: stop and wait` 和 `invalid setpoints`。这两行来自 PX4，不是任务程序的错误，但它暴露了真问题：**退出前没有降落、也没有 disarm**，飞机落地了电机仍处于解锁状态。正确做法是“发降落目标 → 等高度接近 0 → 调 `arming_client` 发 `value: false` 上锁 → 再退出”，这一版没改。
- **机头等待占比过高**：约 70% 的时间花在等 yaw 对齐，见 3.5。
- **短练习 2 只做到推演，未在仿真验证**：思路、掩码、限速与停止条件见第四节，但这一版没有实际跑过，因此没有实测数据。
